# Randly 3.0

Randly — сервис случайного выбора на русском языке: числа, колесо, списки, команды, монетка, кости, да/нет и перемешивание. **Основные генераторы работают без аккаунта и без backend.** Для общих комнат и необязательных аккаунтов используется FastAPI + SQLite. Локальная история и настройки инструментов хранятся в браузере.

## Что было в исходном проекте

Архив `randly_randomizer_v2.zip` содержал одну HTML-страницу и монолитный `app.js`: числовой генератор и колесо. Уже были rejection sampling для 32-битного диапазона, история, исключения, веса и демо-режим. Диапазон был ограничен ±999999 и 2 млн значений; колесо визуализировало числа до 32 секторов. Развитие ограничивали отсутствие тестов и модульной границы, жёсткое ограничение диапазона, а также тесная связь визуализации колеса с числовыми весами. Randly 3.0 оставляет проект статическим и выносит алгоритмы случайного выбора в `random-core.js`.

## Запуск на VPS

Выполните `docker compose up -d --build`. Контейнер доступен только на `127.0.0.1:8788`; подключите внешний Caddy/Nginx reverse proxy и настройте HTTPS на нём. Для подпути используйте проксирование `/randly/` на `http://127.0.0.1:8788/`; ресурсы приложения подключены относительно страницы.

Обновление: `git pull && docker compose up -d --build`. Диагностика: `docker compose ps`, `docker compose logs --tail=100 randly`, `curl -fsS http://127.0.0.1:8788/health`. Остановка: `docker compose down`. Контейнер работает непривилегированным пользователем с read-only root filesystem, без Linux capabilities и с healthcheck.

## Разработка и проверки

Откройте `index.html` в современном браузере или запустите локальный HTTP-сервер из каталога проекта. Основные проверки случайной логики: `node --test tests/random-core.test.cjs`. Требуется Node.js 18+; runtime сайта не требует Node.js.

Алгоритмы используют `crypto.getRandomValues` с rejection sampling без modulo bias. Числовой диапазон может включать отрицательные значения и безопасные целые JavaScript. Без повторов выбор делается за ограниченное число шагов, без случайного перебора до успеха. Веса чисел задаются в настройках как `3:5, 7:2`; для списка — суффиксом `Имя|3` в строке. Незаписанные числа/элементы имеют вес 1, вес 0 исключает значение. Колесо оставляет равные шансы секторам. Пользовательский текст выводится безопасно.

## Ограничения

Сохранённые наборы колеса доступны через команды «Сохранить набор» и «Загрузить набор». История экспортируется в JSON. Поделиться настройками через URL и полноценная английская локализация пока не реализованы. Сброс локальной истории доступен в интерфейсе.


## Аккаунты и общие комнаты (feature branch)
Основной генератор остаётся доступным без входа. На `account.html` можно зарегистрироваться по логину и паролю, создать комнату от 1 до 1000 чисел (например, 1–9) и сохранить настройки между устройствами с помощью кнопок ручной синхронизации.

Комнату можно открыть по адресу `/room.html?code=XXXXXXXXXX`, пригласить гостей ссылкой или QR-кодом. Гостям вход не требуется. Только владелец комнаты может запускать жеребьёвку и очищать историю. Все посетители опрашивают сервер каждые 2 секунды и видят общий результат. Выбор осуществляет серверный модуль `secrets` с равными шансами. В комнате нет скрытых весов или демонстрационных подмен.

Два Docker-сервиса: публичный Caddy `randly` (только `127.0.0.1:8788`) и изолированный FastAPI `randly-api` на внутренней Docker-сети. SQLite хранится в постоянном томе `randly-db` (его удаление удалит аккаунты и комнаты). Для авторизации используются PBKDF2-SHA256 с уникальной солью, случайные токены сессий в HttpOnly SameSite=Strict cookie, а в БД — только их SHA-256. Для продакшена обязателен HTTPS. При проверке через локальный HTTP можно разово задать `RANDLY_SECURE_COOKIES=false` в окружении compose; **никогда не используйте это в публичном развёртывании**.

### Проверка
```sh
docker compose config
docker compose up -d --build
docker compose ps
curl -fsS http://127.0.0.1:8788/api/health
```
Автоматизированные тесты API:
```sh
python -m pip install -r api/requirements.txt httpx
PYTHONPATH=api python -m unittest discover -s api/tests -v
```
Известные ограничения: синхронизация настроек ручная, восстановление пароля не реализовано, нет ограничения количества зрителей в комнате, обновление экрана через polling, а не WebSocket. Нагрузку на 40–100 человек нужно подтвердить отдельным тестом перед публичной эксплуатацией. Не объединяйте ветку в main без завершения проверок.

В подпапке `/randly/` задайте `RANDLY_COOKIE_PATH=/randly/` в окружении Docker Compose. Клиентские запросы к API используют относительные пути, поэтому маршрутизируются через существующий reverse proxy с удалением префикса `/randly/`.


## Приватная панель владельца и бронирование результатов

Новый интерфейс организатора: `/control.html?code=XXXXXXXXXX`. Список своих комнат и переход в панель находятся в профиле `/account.html`. Публичная ссылка для учащихся по-прежнему ведёт на `/room.html?code=XXXXXXXXXX` — это отдельный экран без кнопок управления и без списка броней.

В приватной панели можно указать номер будущего розыгрыша (например, **2**) и желаемое число (например, **9**). Это **подготовленный результат**, а не случайный выбор. После нажатия «Открыть следующий результат» сервер воспроизводит бронь только в указанном розыгрыше и отмечает её типом `prepared`. Незабронированные розыгрыши остаются случайными и имеют тип `random`. При включённом режиме без повторений случайные розыгрыши не используют числа, зарезервированные для будущих шагов.

**Настройка администратора сайта:** бронирование отключено для всех, пока на сервере не задан `RANDLY_RESERVATION_ADMIN_IDS`. Укажите **числовой ID своего уже зарегистрированного аккаунта** в конфигурации окружения Docker Compose, например `RANDLY_RESERVATION_ADMIN_IDS=1`. При необходимости можно указать несколько ID через запятую. Не вписывайте реальный пароль или токен в репозиторий. Узнать свой ID можно в ответе API `GET /api/auth/me` после входа. Владельцы комнат, чьи ID не перечислены в настройке, могут запускать обычную случайную жеребьёвку, но не получают права брони.

**Права доступа:** GET/PUT/DELETE `/api/rooms/{code}/reservations` доступны только авторизованному владельцу конкретной комнаты **с отдельным разрешением администратора сайта**; гостям возвращается 401, другим зарегистрированным пользователям — 403. Публичный GET комнаты **никогда не возвращает номера будущих броней**. Он возвращает только факт наличия подготовленных результатов и источник уже открытых чисел. Скрытие кнопки не заменяет серверную проверку прав, а URL страницы управления сам по себе не считается секретом.

**Прозрачность:** публичная комната обозначает «Подготовленное распределение», если в комнате есть брони. Будущие номера и имена остаются скрытыми; после открытия участник и число появляются, например, как «Максим — задание №7». Не выдавайте подготовленные результаты за равновероятную жеребьёвку.

**Сброс:** очистка истории возвращает счётчик шагов к первому розыгрышу; подготовленные брони остаются и могут быть воспроизведены снова. Уже открытые брони нельзя изменять/удалять до сброса истории. Для режима без повторов значения броней должны быть уникальны и входить в диапазон комнаты.

**Проверка:** `python -m unittest discover -s api/tests -v` включает регрессионные тесты приватности, разграничения прав, сохранения и открытия броней.

## Самостоятельное открытие задания участниками (self-service)

**Режим отдельный от обычной случайной жеребьёвки.** На странице аккаунта администратор сайта с ID, указанным в `RANDLY_RESERVATION_ADMIN_IDS`, при создании комнаты может отметить «Участники сами открывают задания по личной ссылке».

1. В панели `control.html?code=...` организатор создаёт назначения: номер слота, число в диапазоне и имя человека или существующий `@логин`. В режиме без повторов нельзя назначить один номер двум участникам.
2. Для каждого назначения нажимает «Личная ссылка». Сервер создаёт криптографически случайный токен, сохраняет **только SHA-256 хеш**. Полная ссылка появляется в панели только один раз после выдачи, поэтому её нужно скопировать и отправить нужному ученику.
3. Участник открывает `participant.html?code=...#ticket=...` на телефоне. Токен передаётся в **URL-фрагменте**, который браузер не отправляет серверу при обычном GET. Только при нажатии «Открыть моё задание» браузер отправляет токен в теле защищённого POST-запроса к `/api/rooms/{code}/reveal`.
4. Сервер атомарно открывает назначение по билету и сохраняет в `room_self_reveals`. Двойное нажатие / повторное обращение возвращает **то же самое число**. В публичную комнату и историю результат попадает только после открытия; название режима «Подготовленное распределение» видно всем.
5. Выдача новой ссылки **отзывает старую** до открытия задания. Уже открытые назначения нельзя заменить, удалить или перевыпустить. После сброса истории те же билеты могут открыть результаты снова.

Личные ссылки имеют **bearer-доступ**: любой, кто получит ссылку, сможет открыть именно это задание. Это подходит для обычных занятий, но не является подтверждением личности ученика. Не публикуйте персональные ссылки в общем чате. Логины пользователей используются для подписи назначения, а не для замены проверки токена. Гостям не нужно создавать аккаунт.

Комнаты в этом режиме **не выполняют случайные розыгрыши**. Владельцу доступны сброс результатов и просмотр общей истории; каждый участник открывает только своё подготовленное задание. Обычные комнаты продолжают работать без изменений. До публикации проверьте поведение на телефонах через реальный HTTPS.
